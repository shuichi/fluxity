01 / MODELモデルと原典の位置づけ

Fluxityは、一人ひとりを位置・速度・半径・目的地を持つエージェントとして扱う平面上の微視的群集シミュレーションです。歩行判断はCPUのWeb Workerで行い、その結果をWebGPUで3Dの人物として描画します。GPU Computeで歩行者の運動を解いているわけではありません。

この版の対象範囲

2026年11月25日版では、信号待ちの視線、分岐での迷い、すれ違いの判断と接触時の姿勢を扱います。本文は公開前の作業ツリーを説明しています。従来の模擬交差点の基準版は27e3b045です。末尾のmainリンクは変更の公開後の参照先で、公開前には本文と一致しない場合があります。参考文献の確認日は上記のとおりです。

中心となる組み合わせは、目的地別のDijkstra距離場による大域誘導と、近距離反発・前方減速と、最近接予測に基づく通過方向の選択です。人物は地面上では円として近似され、表示用の腕や脚には独立した衝突判定を行いません。

02 / PIPELINE1ステップの処理

通常の実行では、以下を1/30秒ずつ進めます。人物の位置・速度は全員分を読み取り用の状態から参照し、計算結果を別の状態に書いて、最後に交換します。

  1. 信号を更新次のシミュレーション時刻で赤・青を判定。
  2. 空間を索引化現在位置から近傍探索用のグリッドを再構築。
  3. 目的地へ誘導到着判定後、直進または共有方向場を参照。
  4. 赤信号で減速車道への進入を抑え、信号待ちの人は個別の間隔で周囲を見る。
  5. 人・壁を回避衝突の予測から直進・左右・減速を比較し、反発と合成。
  6. 運動を積分加速度と速度を制限して次の位置を計算。
  7. 境界を補正建物・歩道・横断歩道の外への移動を修正。
  8. 状態を交換向き・歩行位相・統計を更新し、描画へ渡す。

実装：Simulation.step、AgentData.swap。Workerは1回の起動で最大3ステップ進めてから最新状態を送るため、描画用Snapshotは必ずしも全ステップ分届きません。

03 / GLOBAL NAVIGATION目的地を共有するフローフィールド

歩ける領域をグラフにする

PLATEAU版の渋谷では、交差点中心の250m四方を一辺0.75mの格子へ分割します。歩道と横断歩道の和集合から建物の接地輪郭・交通島・植栽を除いた、穴付きポリゴンが通行可能領域です。セル中心には境界から0.34mの余裕を要求します。広場や通路など既存の他シナリオは、1.5m格子・0.58mの余裕と軸平行長方形（AABB）を引き続き使います。

通行可能セルを頂点、上下左右と斜めの8近傍を辺とするグラフを作ります。辺の重みは直進が1、斜めが√2です。斜め移動では両側の直交セルも通行可能にします。PLATEAU版ではさらに、隣り合うセル中心を結ぶ線分全体が0.34mの余裕を含めてポリゴン内を通るか検査し、細い障害物や穴を飛び越す接続を除きます。

目的地から逆向きにDijkstra法を実行する

各目的地を始点として、全セルの最小コストを求めます。非負の辺重みに対する最短路法の原典はDijkstra（1959）です。コードでは添字付き二分ヒープを使い、距離が小さいセルを優先して緩和します。[1]

D(goal) = 0、その他の D = ∞
未処理の最小 D を持つセル u を取り出す
  各通行可能な隣接セル v について
    D(v) ← min(D(v), D(u) + w(u,v))
w = 1（直交）または √2（斜め）

コードでは浮動小数の比較に10⁻⁴の許容値を使用。格納するDはセル単位のコストであり、そのままメートルではありません。

得られた距離場から、各セルの周囲でDが最も小さい隣接セルを選び、その方向を正規化して保存します。人数分の経路を毎回探索せず、同じ目的地の人物が場を参照できます。目的地数をT、セル数をVとすると、構築は概ねO(TV log V)、場の保存はO(TV)です。

渋谷では各出入口の歩道側の到達点を目的地として場を共有します。全目的地へ到達できない孤立した庭などのセルは有効グリッドから除外します。目的地同士が分断されている場合は初期化をエラーにし、接続不良のまま群集を生成しません。

近距離の見通しと、方向場の先読み

PLATEAU版では、個別目標まで10m以内で、人物半径に0.015mを足した余裕を含めて直進できる場合、その目標へ直接向かいます。それ以外は周囲3×3セルから見通せる候補を D + 0.1 × 現在位置からの距離 で選び、保存した方向場を最大3セル分先読みします。見通せる範囲までを誘導点にすることで、各人から遠方の目的地まで長いポリゴン照合を毎回行う処理を避けています。

ポリゴンの包含判定には穴も含む境界との交差回数を用い、半径の余裕には境界辺までの距離を調べます。1m幅の行と4m四方の区画で辺を索引化し、点・線分・近接境界の照合候補を絞ります。方向場をセル間で双線形補間する処理はありません。

AABBを使う他シナリオでは従来どおり、目標への見通しがあれば直接誘導し、なければ方向場を参照します。固定0.58mの余裕を付けたAABBとの線分交差はスラブ法で判定します。各軸のパラメータ区間を交差させる考え方はPBRTでも説明されています。通行不可セルでは周囲5×5から回復先を探します。[12]

距離場と、人物が実際に歩く道筋は区別が必要です。距離場はDijkstra法で求めますが、方向抽出は argmin D(v) であり、argmin(w(u,v) + D(v)) ではありません。直接誘導・目標の分散・局所回避も加わるため、人物の軌跡全体を厳密な最短経路とは呼べません。

Emerson（2013）は、ゲームで共有するコスト場・積分場・方向場の構成を説明しています。Fluxityはこの設計と共通点を持ちますが、タイル階層・ポータル探索・動的な場の再構築はありません。Treuilleら（2006）のContinuum Crowdsのように群集密度を使って場を毎フレーム更新したり、Eikonal方程式を解いたりもしません。[2] [8]

実装：Navigation.constructor / buildField / urbanDirection / direction / lineOfSight、UrbanGeometry / PolygonRegion。

04 / SPATIAL QUERY近くの人だけを高速に探す

全員が全員を調べると候補数はO(N²)になります。Fluxityは、経路探索用とは別に、一辺2.4mのUniform Gridを使います。空間分割で接近し得る組だけを調べる手法の技術的参考として、Le Grand（2007）のBroad Phase解説を挙げます。これは本実装のCPU版そのものの出典や、Uniform Gridの発明者という意味ではありません。[9]

  1. 各人物が属するセルを求め、セルごとの人数を数えます。
  2. 人数の累積和（prefix sum）から、各セルが使う配列区間を求めます。
  3. 人物IDをセルごとの連続領域へ配置します。比較ソートは使わず、Counting Sort型に並べます。

再構築はO(N+C)です（Cはこの近傍グリッドのセル数）。各人物は自分のセルと周囲8セルを走査し、距離が2.4m以下の相手を局所回避に使用します。配列は再利用され、通常の再構築で人物ごとの配列・オブジェクトを生成しません。

上限96は「調べる候補数」です。自分以外の候補を数えてから距離を判定するので、距離外の人も96件に含まれます。最も近い96人を選ぶ処理ではありません。セル内の開始位置を人物IDで回転させていますが、セルの走査順は固定であり、密集時の偏りや見落としは残ります。

近傍計算の上限はO(96N)になりますが、この上限は正確さとの交換条件です。予測の相手は現在距離2.4m以内に限られ、速く接近する相手が範囲へ入ってから回避が始まる場合があります。

実装：SpatialGrid.rebuild、Steering.compute。

05 / LOCAL STEERING反発・減速・予測を混ぜる局所回避

ReynoldsのBoids（1987）は局所的な行動から群れの運動を作る代表的な原典で、Steering Behaviors（1999）は目標追従や回避などの行動を整理しています。Fluxityの局所回避はこの系譜に位置づけられますが、以下の係数と組み合わせはコード固有のヒューリスティックです。[3] [4]

pᵢ, vᵢ, rᵢ
人物iの位置・現在速度・半径。
dᵢ, sᵢ
誘導方向と、このステップでの希望速度。分岐で迷っている間は速度に個人の減速倍率が掛かる。通常のdᵢは単位ベクトル。
q, R
相対位置 q = pⱼ − pᵢ、半径の和 R = rᵢ + rⱼ。
right(dᵢ)
右向きの成分 (dᵢ.z, −dᵢ.x)。
k
Avoidance設定（0〜3、初期値1）。

赤信号で減速した後のdᵢは、成分を弱めたまま再正規化しません。以下の内積もそのdᵢを使うため、赤信号付近の「前方距離」は厳密な単位方向への射影ではなく、制御上の量です。

5.1 パーソナルスペースの反発

相手までの距離が R + 0.34m 未満なら、相手から離れる成分を足します。これは速度への補正であり、人物同士のめり込みを幾何学的に必ず解消する位置補正ではありません。

δ = |q|
c = 通常は3.6、相手が出入口を通行中なら8
Sᵢⱼ = −(q / δ) × min(2.4, c × (R + 0.34 − δ))
Sᵢ = 条件 δ < R + 0.34 を満たす近傍の Sᵢⱼ の総和

位置がほぼ一致する場合は、IDの大小で符号が反対になる微小ベクトルを使い、ゼロ除算と完全な対称状態を避けます。

5.2 前の人に追いつくと減速する

前方成分 f = q・dᵢ が0〜1.8m、横方向成分の絶対値が R + 0.2m 未満で、相手との前方速度差が0.15m/sを超える場合に減速します。

c = q.x × dᵢ.z − q.z × dᵢ.x
closing = sᵢ − vⱼ・dᵢ
b_follow = (1 − f / 1.8) × min(0.85, closing × 0.5)
brake = 対象となる近傍の b_follow の最大値

5.3 最近接時刻を予測し、直進・左右・減速を選ぶ

自分が希望速度 sᵢdᵢ、相手が現在速度 vⱼ を維持すると仮定します。相対位置の二乗距離 |q − wt|² をtで微分して0と置くと、最近接時刻t*が得られます。

w = sᵢdᵢ − vⱼ
t* = (q・w) / |w|²
δ* = |q − wt*|
u = (1 − t* / Hᵢ) × (1 − δ* / (R + 0.35))

f > 0、|w|² > 0.08、0 < t* < Hᵢ、δ* < R + 0.35m のとき、衝突のおそれがあると判定します。Hᵢは歩行者ごとの先読み時間で1.4〜1.85秒。緊急度uが最も高い相手を記録し、1.25u が0.075を超えると、通常の歩行では次の候補を評価します。

試す速度は、前方・右方向の順に希望速度に対する倍率で表すと、直進（1, 0）、右へ（0.88, 0.64）、左へ（0.88, −0.64）、譲る（0.35, 0）です。進路前方の空きを評価するため、q・dᵢ < −0.3 の後方の相手をこの比較から外します。その他の近傍は現在速度を維持すると仮定し、各候補の先読み時間内で最も危険な接近を評価します。そこに基礎コストを加えます。直進は0、右は0.08、左は0.25、譲る場合は人によって0.11〜0.28です。すでに片側を選んでいる場合、異なる側・直進・減速への変更には0.36を加えます。後方から来る人にも近距離の反発は働きます。

評価がよい候補から、0.65秒先まで壁・路面・赤信号の制約に収まるかを調べます。すべて通れない場合も減速を選び、最終位置は§6の境界処理で確定します。危険が続く間は約0.42〜0.62秒おきに判断を見直し、最後に判断を必要とする危険を検出してから0.38秒、選択を記憶します。横へよける方向が新しく決まり、衝突予測まで0.65秒を超える余裕があれば、横方向の補正を0.12秒かけて立ち上げます。急接近時はすぐに回避します。

歩行に適用する補正の強さは、その時点の危険に合わせます。左右を選んだときは、候補の相手がいる間、横方向の補正に希望速度の0.30倍を下限として設けます。譲るときは min(0.62, 0.22 + 0.46 × 最大緊急度) を減速係数の下限にします。予測上の相手がいなくなれば両方の補正を解除し、次の瞬間に同じ相手が再び現れたときのために選択だけを短く保ちます。戸口付近では戸口の通行制御が優先されます。四候補を比較するのは、戸口用に指定されたセルの外で、希望速度とAvoidanceがともに正のときです。

FioriniとShiller（1998）のVelocity Obstaclesは、相対運動から衝突を起こす速度の集合を扱う原典です。Fluxityでは四つの速度候補を比較し、選んだ通過方向や減速を既存の歩行制御へ反映します。ORCAは各歩行者の回避負担を分け、半平面制約から速度を求める手法です。[5] [6]

5.4 合成・滞留脱出・壁回避

v_desired = sᵢdᵢ × (1 − brake × min(1,k))
          + k × (Sᵢ + lateral × right(dᵢ))
          + 戸口で通行者に譲る成分 + 滞留時の右寄せ + 壁・外周からの反発
最後に |v_desired| を 1.12sᵢ 以下へ制限

速度が希望速度の20%未満の状態が2秒を超えて続くと、希望速度が正の場合に 0.3 × right(dᵢ) を追加します。対称な対向流の膠着を緩めるためのルールですが、必ず脱出できる保証はありません。

PLATEAU版では歩行可能ポリゴンの最寄り境界からの距離が rᵢ + 0.75m 未満なら、境界から内側へ向かう成分を加えます。他シナリオでは建物AABBの最近点を使います。シーン外周にも同様の反発があります。これらと滞留脱出はkの乗算の外にあるため、Avoidanceを0にしても壁・信号・滞留脱出の処理は残ります。

5.5 肩が触れた後の反応

円として表した体が接し、実際の相対速度のうち相手に近づく成分が0.22m/sを超えたとき、接触側と逆に上体を短く傾けます。傾きは接近速度に応じて最大0.21radとなり、通常歩行では一時的な減速にも使います。体の間隔が半径の和＋0.055m以内の間は同じ接触として扱い、この距離を離れて約0.24秒経過すると次の反応が可能になります。混み合って肩を並べて立っている間に、反応だけが繰り返されることを防ぎます。

実装：EncounterState、Steering.compute / chooseManeuver。LocalAvoidanceを置き換えれば、経路探索やWorker通信を維持したまま別の回避法を導入できます。

06 / MOTION速度を更新してから位置を進める

希望速度へ即座に切り替えず、0.3秒の応答時間を使って加速度を求め、通常の加速・減速を滑らかにします。

a = (v_desired − v) / 0.3
a ← 長さを最大 3.8 m/s² に制限
v′ = v + aΔt
p′ = p + v′Δt
Δt = 1/30 s（通常のWorker実行）

速度を先に更新するので、運動更新はsemi-implicit Euler型です。ここでの加速度は運動制御の補正値で、質量・接触力・摩擦を解く剛体力学モデルではありません。速度設定を下げた場合には、現在速度から3.8m/s²で減速できる値も上限計算に含め、一瞬で速度を切り落とさないようにします。

壁との接触は位置を補正する

位置更新後、外周へクランプします。PLATEAU版は開始点から予定点までを半径付きの線分として検査し、歩道・横断歩道の外や建物輪郭の穴を横切る場合は、接触手前で止めて境界に沿う移動を残します。他シナリオの建物は従来の拡張AABBで押し戻します。最後に v = (補正後位置 − 旧位置) / Δt として実際の移動速度を再計算します。

そのため、3.8m/s²という上限は位置補正を含めた全変化を保証する上限ではありません。PLATEAU版の線分検査は静的な平面ポリゴンに対するものです。動く障害物や任意の3D形状を扱う連続衝突判定（CCD）、人物同士の接触拘束は実装していません。AABBを使うシナリオでは角まで拡張する保守的な近似が残ります。

身体の向きと歩行アニメーション

速度が0.045m/sを超えると、移動方向 atan2(vx, vz) へ、最短の角度差を使って最大3.5rad/sで身体の向きを近づけます。これは見た目の向きの制限で、速度ベクトル自体の旋回速度を制限する処理ではありません。

歩行位相は phase += speed × Δt × 4.5 とし、移動距離に連動させます。位相を毎回2πへ折り返さないことで補間の継ぎ目を避けます。速度0.06m/s未満はIdle、2.2m/s超はRun、それ以外はWalkとして描画へ渡します。

首の向きと、分岐で一瞬迷う動作

信号待ちでは、赤信号による縁石での減速に入った人にだけ、次に見回すまでの時間を割り当てます。待ち時間は0.65秒に指数分布の時間を加え、周囲への関心が高い人ほど平均の間隔を短くします。見る先は、進みたい横断歩道の向こう側、その側にあるこちら向きの信号、近くを歩く人です。すれ違いでは、横へよける判断をした人の一部が、通る隙間に先に顔を向けます。首は身体に対して左右最大1.18rad、最大2.8rad/sで動き、一度選んだ方向を0.45〜1.05秒見てから正面へ戻します。人物視点のカメラも首の向きを反映します。

分岐の判定は、一人ずつ時刻をずらして行います。交差点の入口や障害物の手前で、目的地に向かう11方向を10m先まで調べます。通れない地面で分かれた二つの進路がどちらも目的地に近づき、残りの経路長の差が3.5m以内なら、迷う余地があります。その場所に来たときに一度、道に慣れている度合いに応じた確率で反対の候補にも顔を向け、0.55〜1.25秒の間、希望速度を35〜62%にします。その後は元の目的地へ進みます。渋谷の横断中や赤信号待ち、戸口での通行制御中には、この減速を加えません。

実装：PedestrianAttention、Navigation.alternativeAtFork、Simulation.step / writeSnapshot。

07 / SHIBUYA SCRAMBLE横断歩道の幅を使い、赤になったら歩道へ導く

渋谷ステージはPLATEAU渋谷区2025年度の建物・道路データを使います。建物はLOD2を優先し、背景は約500m四方、歩行計算は中心250m四方に限定します。元データの歩道に、地理院空中写真を参照して調整した駅前広場・植栽除外と5本の横断歩道を重ねています。横断歩道の幅は6.5〜11mのデモ設定で、測量済みの路面標示や現在の信号設備を表すものではありません。

歩道と横断歩道のポリゴンは取り込み時に和集合・差集合を計算し、描画と経路探索の共通データにします。横断歩道の白線は車道面で切り抜きます。描画バイナリのSHA-256を地図に記録して読み込み時に検証するため、異なる版の建物・路面と歩行領域を組み合わせて実行しません。地面は平坦化し、建物は元の形状を保って建物ごとの最低標高を差し引きます。坂道・駅構内・デッキ・地下通路の多層移動は対象外です。

目的地までの経路が横断歩道を通るときは、歩道にいるうちに各人が横断位置を選びます。候補は両側の歩道がつながり、身体の幅を含めて通れる位置です。一方向の流れは横断歩道の幅いっぱいに広がり、対向する人が増えると、それぞれが進行方向の右側を多く使います。途中で赤になった人には、歩道へ退避する経路を優先します。

赤：新しい横断を抑止

現在歩道上にいる人は、車道へ向かう希望方向の成分を弱め、最終位置も歩道側に制限します。

踏み出して1.5m以内で元の歩道に戻れる人は引き返し、ほかの横断者は小走りで渡り切ります。着地点の前で待っている人は、歩道内で横や後ろへ道を譲ります。

青：横断を開始

信号による歩道限定の制約を外し、歩道と横断歩道の和集合を移動可能にします。

歩行者同士の回避と、横断歩道の外へ出ない制約は継続します。

停止線への接近と、位置制約の二段階

赤で歩道にいる人について、進行方向にある歩道境界を調べます。信号待ちの注視対象は、縁石で方向を弱める前の進路から選びます。境界の先が歩行可能な横断領域へ開いている場合だけ停止対象とし、建物壁は停止線として数えません。停止位置までの進行方向距離が3m未満なら、歩道境界の法線方向の成分を弱めます。法線方向の減速幅は2.2m、停止位置には有効半径に加えて0.08mの余裕を設けます。減速を局所回避より前に適用し、境界に平行な移動は残します。

局所回避の押し出しで車道へ入らないよう、最後にも歩道ポリゴン内へ移動を制約します。歩道内の判定・経路誘導・減速・移動制約・横断人数は、いずれも人物半径＋0.015mで統一します。全身が歩道を離れ始めたときに入口を記録し、赤の最初の歩行ステップで戻る側か渡る側かを決めます。途中で青に戻っても、全身が歩道に収まった時点で元の旅程に復帰します。

渡り切る人の希望速度は通常の最大1.7倍です。小走りへの上乗せは2.8m/sまでで、すでに速い人は設定どおりのペースを保ちます。横断者は2秒ごとに進み具合を確認し、進めないときは同じ出口の幅の中で着地点を探し直します。目指す歩道の縁石が1.2m以内なら、身体が収まる位置へまっすぐ上がれるかを先に確かめます。候補の混雑度には空間グリッドの人数を使います。曲がり角では歩行可能な経由点をたどります。出口で手前の待機者だけでは通路を空けられないときは、その後ろにいる人も歩道の奥へ下がります。

線分を検査してから、境界に沿って滑らせる

PolygonRegion.lineInsideは始点・終点の包含に加え、移動線分と境界の交差、線分と各境界辺の最短距離を調べます。終点だけが有効でも、その途中で建物の穴や領域外を横切る移動は採用しません。境界は空間索引で絞り込みます。

予定移動が通れない場合は、最大12回の二分探索で接触手前を求め、残った移動から外向き法線成分を除去します。この処理を最大2回行い、横断歩道の端に沿う移動を残します。Float32への格納で境界外に丸められたときは、最大4回の微小な内側補正を試します。補正量は予定移動距離を超えないようにし、安全な表現可能位置が得られなければ元の位置を維持します。

旧来の十字型交差点は、synthetic-shibuya.tsという回帰テスト用fixtureとして残しています。そのScrambleGeometryは歩道・横断歩道の区間の和集合と凸領域への投影を使います。現在のPLATEAU地図はUrbanGeometryを通り、原点中心の十字道路や4隅の前提を使いません。

自動周期はシミュレーション時計で進む

τ = simulationTime mod 47
0 ≤ τ < 12  → 赤
12 ≤ τ < 47 → 青
手動Red / Green → 指定した色に固定、残り時間はなし

周期は赤12秒＋青35秒です。実装では境界の丸め誤差を抑えるため時刻に10⁻⁹秒を加えて剰余を取ります。Pause中は時計が進まず、速度倍率はこの時計の進み方にも作用します。Autoへ戻すと現在時刻の位相に復帰し、赤から周期をやり直すわけではありません。

これは本実装のデモ用ルールです。車両との協調、青の点滅、横断完了に応じた延長、実際の渋谷の信号周期はモデル化していません。

実装：TrafficSignal、CrosswalkFlow、CrossingClearance / CrossingExits、UrbanGeometry / PolygonRegion、shibuyaシナリオ、layout.json、import-plateau.py、UrbanMeshLoader、Simulation.step。

08 / TIME & DATA計算の時計と、画面の時計を分ける

固定刻みと、追いつき処理の上限

固定時間刻み・accumulator・描画補間の実用的な参考はFiedler（2004）です。時間刻みを一定にすることで、描画フレームレートの変化を運動計算へ直接持ち込まずに済みます。この文献を固定刻み数値積分そのものの発明の原典とは位置づけません。[10]

Workerは8ms間隔のタイマーで起動しますが、タイマーは正確な周期を保証しません。実時間差を最大0.1秒に制限し、速度倍率を掛けてaccumulatorへ足します。蓄積は最大3Δt、一度に実行するのは最大3ステップです。遅れが大きいときは余剰時間を捨てるため、負荷が高い場合のシミュレーション時刻は実時間より遅くなります。

SoAと二重状態

人物ごとのオブジェクトではなく、x[]、z[]、vx[]などのTypedArrayを並べるStructure of Arrays（SoA）形式です。運動状態をcurrent/nextの2組で保持し、全員の計算が終わってから交換します。これにより、同じステップ内で先に計算した人の新しい位置を、後の人が読んでしまう非対称性を避けます。ただしIDや候補順序への依存まで消えるわけではありません。

Snapshot転送と表示補間

WorkerのSnapshotは、身体の向き・首の角度・接触時の傾きを含む1人15個のFloat32、60バイトです。GPUに送る人物は4個のvec4、1人64バイトにまとめ、首と上体を頂点シェーダーで動かします。Workerが用意した4個のArrayBufferをTransferableとして受け渡しし、メインスレッドは直前と現在の2状態を保持します。空きバッファがなければ中間Snapshotの送信を省略し、返却時に最新状態を送ります。世代番号でリセット前のデータを除外します。

p_render = (1 − α) p_previous + α p_current
α = clamp((受信後の実時間 × 速度倍率) / Snapshot間のシミュレーション時刻差, 0, 1)

Snapshot間のシミュレーション時刻差が0の場合はΔtを代用します。これはCPUの処理時間ではありません。向きは最短の角度差、歩行位相は連続値で補間します。受信時刻を基準にするため、Fiedlerの記事のaccumulator比率をそのまま使う実装ではありません。αは1で止まり、未来位置への外挿は行いません。通常は約1ステップ分遅れた状態を滑らかに見せ、転送が間引かれた場合はより広い状態間を補間します。同じスロットが別人に入れ替わった場合は人物の世代番号で判別し、新しい人物の位置から表示します。

Workerは1本です。描画スレッドと計算スレッドは並行しますが、人物の更新を複数のCPU Workerへ分割する方式ではありません。

実装：SimulationWorker、AgentData、SnapshotTimeline、InstanceBuffer.update。

09 / REPRODUCIBILITY初期化・目的地更新・再現性

乱数はseedから生成し、体格・速度差・外観・初期配置・目的地の分散に使用します。Random.nextの定数 0x6d2b79f5 と乗算・XORの構成は、Ettinger（2017）のMulberry32に対応するものです。[11]

ただし本実装の状態変数はJavaScriptのNumberで、加算のたびに32bitへ折り返す処理はありません。原典の32bit整数状態と完全に同じ長周期特性を保証するとは記述しません。通常の再現性は同じコード・seed・設定・ステップ列・設定変更のタイミングを前提とし、ブラウザ間の全演算のbit単位一致まで検証していません。

周囲を見る頻度・道への慣れ・衝突の先読み時間・譲る傾向は、シード、人物スロットID、人物の世代から決めます。注視の間隔や持続時間には各人物専用の乱数列を使います。出入口でそのスロットが別人に入れ替わると、性向と行動タイマーも新しくなり、直前の人物の姿勢は引き継ぎません。

初期配置は試行回数を制限した拒否サンプリング

スポーン領域から候補点を取り、通行可能性と既配置人物との距離を調べます。最大100回まで試し、密集時には間隔条件を緩めます。渋谷の候補点は、目的地へ到達できる歩道に限定します。最後の候補が無効なら、あらかじめ検査した有限の歩道セル一覧から選び直します。同じスポーン領域内のセルを優先し、候補がなければ共通一覧を使います。有効なセルが一つもなければエラーにするため、空の地図で無限に探索し続けません。これは厳密なPoisson Disk Samplingや、全員の非重複を保証する配置法ではありません。

出入口を通って街を出入りする

歩行者は共有経路をたどり、建物入口や街路端に設けた短い通路を最後まで歩きます。建物では戸口の奥に姿が隠れ、街路では外周区間で人物と接地影が徐々に見えなくなります。

渋谷の5店舗と北の街路端では、歩道上の人が前方2.2 m以内に見える相手の位置と速度から進路の交差を予測します。相手がほぼ止まっているときは体の向きを手がかりにします。壁や手前の人で相手が隠れるかも調べます。譲る側は、出入口を通り始めた人や、出入口により近い人を先に通します。歩道上の空きへ一歩よけ、空きが見つからなければ短く待った後、自分の目的地へ向かいます。

店舗に向かう歩行者は、目的の戸口から2〜17 mの歩道で、前の人の進み具合も見ます。店に近い側の人がほぼ停止していて、身体の間隔が一歩分（0.70 m）を切ると、後続は減速し、0.35秒待ってから進路を見直します。横断歩道を渡り切る動作を優先します。

戸口に斜めに並ぼうとする人は、店から出てくる人が見えると、その人が歩道に上がるまでの進路を確認します。1 m以内で進路が重なるとすぐに譲ります。もう少し離れている間は、どちらかが0.6秒以上足止めされたときに譲ります。すでに進路を塞いでいれば、歩道上で肩がぶつからない場所へ半歩退きます。入店途中でまっすぐ進めなくなった人は、自分のレーンの幅の中で斜めに足を出せるかも確かめます。

戸口に幅があるときは、店から出る人の通り道を空けて、店に入る人は戸口の脇で待ちます。戸口とその手前では、体格に応じた肩幅を使い、各ステップの途中も含めて近くの歩行者との間隔を調べます。前の人が進めばその分だけ前進し、歩道を横切る人が進路をふさいでいる間は待ちます。歩道側に横へよけられる空間があれば、壁や縁石までの余裕を確かめてそちらへ進みます。初期配置でも戸口付近の間隔を保ちます。

一人が退出すると、同じステップに別の出入口から一人が登場します。出入口の幅と空きを考慮して入場位置を割り当て、混雑時は空きができるまで退出を待つため、シミュレーションの総人数は一定です。初回の配置だけは広いスポーン領域を使います。

実装は Simulation、DoorwayCourtesy、DoorwayHeadway と PortalFlow、渋谷の出入口配置を参照してください。

表示される統計の定義

  • Mean speed：境界補正後の移動速度の全員平均。

11 / VALIDATION & LIMITS何を検証し、何を保証しないか

対象コードには、seedによる再現性、障害物を迂回する到達、グリッドの索引、対向2人のすれ違い、加減速と向き、赤信号での進入抑止、横断中の継続、端に沿う移動、Snapshotの所有権などの自動テストがあります。PLATEAU対応では、穴付き・回転ポリゴン、孤立領域、出口の縁とFloat32丸め、実地図の目的地連結、1,000人の赤青切り替え、20,000人の初期化と短時間の領域検査、地図とバイナリの版一致を追加しました。

参照：シミュレーション・信号・地図・読込のテスト一覧。テストが扱う条件で性質を確認しているのであり、任意の密度・配置・速度・実行時間で成立する数学的証明ではありません。

境界実装上の意味
人物同士の重なり通常の歩道では速度補正で回避する。接触時に姿勢を変えて減速するが、過密時や候補の見落としで体が重なり得る。戸口には専用の通行制御がある。
渋滞・デッドロック通過側の保持・譲り合い・滞留脱出で軽減するが、出口の混雑や対向流の膠着を必ず解消する保証はない。
最短経路・動的混雑静的な共有場。混雑で大域経路を再最適化せず、個別軌跡の最短性も保証しない。
境界と大きな刻み渋谷は静的な平面ポリゴンに対する半径付き線分検査と滑り補正。他シナリオは従来の制約を使う。動く障害物や多層3DへのCCDではない。coreのstepは0超〜0.1秒を許すが、Workerは1/30秒固定。
地図と高さPLATEAUの版年は形状の取得年ではない。地面は平坦化し、横断歩道・信号位置・駅前補正はデモ用の調整。地表の建物輪郭で移動を制約し、屋根形状を歩行衝突に直接使わない。
実測との対応歩行速度差・視線や迷いの発生率・回避コスト・信号周期はデモ設定。実在の渋谷の流量・避難時間・安全性の予測用に校正していない。
計算量と性能近傍探索には上限があるが、描画・障害物数・領域判定なども時間を使う。全端末・全人数で30Hzや60FPSを保証しない。

人数N、近傍セル数C、各人のポリゴン判定で調べる辺などの総量をQᵢとすると、PLATEAU版の通常ステップは概ね O(N + C + 96N + ΣQᵢ) に近い構成です。空間索引と短い先読みでQᵢを減らしますが、地図形状に依存し、常に一定時間という保証ではありません。AABBを使う他シナリオには人数×障害物数の走査が残ります。初期化・Dijkstra場の構築・GPU描画はこの目安に含みません。

より厳密な回避が必要ならLocalAvoidanceをORCAなどへ置き換え、動的な混雑を考慮するなら誘導場の更新方式を変更できます。その場合も、各方式の仮定と高密度条件での限界を改めて検証する必要があります。
