01 / MODEL実装している手法と比較対象

Fluxityは一人ひとりの位置・速度・半径・目的地を持ち、地面上の人を円として扱います。目的地までの大まかな進路は共有フローフィールドで決め、次の一歩は各人の周囲を見て決めます。この計算はCPUのWeb Workerで行い、結果をWebGPUで3D表示します。

02 / PIPELINE1ステップの処理

Workerは1/30秒ずつシミュレーションを進めます。局所回避はステップ開始時の近傍位置・速度を読み、確定した移動先は別の配列に書きます。戸口の間隔確認には先に動いた人の移動先も使います。信号と車両の処理は渋谷シナリオで実行します。

  1. 信号を更新渋谷では時刻と交差点に残る車・歩行者を確認し、各方向の灯色を更新。
  2. 周囲の人を索引化現在位置からグリッドを再構築。渋谷では出入口付近で誰が譲るかも判定。
  3. 歩く方向を決定通常は直進または共有方向場で誘導。渋谷の横断中は横断歩道上の進路や退避先へ誘導。
  4. 歩行速度を調整渋谷では青点滅・赤で縁石への接近を抑制。分岐での迷いや、近くの人との距離・接近予測を反映。
  5. 歩行者の位置を確定通常歩行は加速度・速度を制限して積分。境界と車体を確認し、実際の変位から速度・向き・歩行位相を更新。
  6. 車両を移動渋谷では歩行者全員の移動が決まった後で、信号・前車との間隔・歩行者の移動線分を使って走行を更新。
  7. 出入りを反映退出が成立した歩行者の配列位置を、別の出入口に登場する人物に引き継ぐ。
  8. 状態を交換新しい配列を現在状態にし、時刻・平均速度・混雑率などを更新。

出入口で通行レーンに整列する人や、その中を移動する人の位置は PortalFlow.move が直接決めます。この間は通常歩行の経路誘導・局所回避・積分を省きます。Workerは1回のタイマー処理で最大3ステップ進めた後、最新の描画用Snapshotを送ります。

実装箇所　Simulation.step / writeMotion、AgentData.swap、SimulationWorker。

03 / GLOBAL NAVIGATION目的地を共有するフローフィールド

歩ける領域をグラフにする

PLATEAU版の渋谷では、交差点中心の250m四方を一辺0.75mの格子へ分割します。歩道と横断歩道の和集合から建物の接地輪郭・交通島・植栽を除いた、穴付きポリゴンが通行可能領域です。セル中心には境界から0.34mの余裕を要求します。広場や通路など既存の他シナリオは、1.5m格子・0.58mの余裕と軸平行長方形（AABB）を引き続き使います。

通行可能セルを頂点、上下左右と斜めの8近傍を辺とするグラフを作ります。辺の重みは直進が1、斜めが√2です。斜め方向の辺を使えるのは、両脇の直交セルも通行可能な場合です。PLATEAU版ではさらに、隣り合うセル中心を結ぶ線分全体が0.34mの余裕を含めてポリゴン内を通るか検査し、細い障害物や穴を飛び越す接続を除きます。

目的地から逆向きにDijkstra法を実行する

Fluxityは初期化時に、目的地ごとにDijkstra法を実行します。始点は目的地のセルです。そこが通行不可なら最寄りの通行可能セルを使います。添字付き二分ヒープから距離が最小のセルを取り出し、隣接セルのコストを更新します。[1]

D(goal) = 0、その他の D = ∞
未処理の最小 D を持つセル u を取り出す
  各通行可能な隣接セル v について
    D(v) ← min(D(v), D(u) + w(u,v))
w = 1（直交）または √2（斜め）

コードでは浮動小数の比較に10⁻⁴の許容値を使用。格納するDはセル単位のコストであり、そのままメートルではありません。

得られた距離場から、各セルの周囲でDが最も小さい隣接セルを選び、その方向を正規化して保存します。人数分の経路を毎回探索せず、同じ目的地の人物が場を参照できます。目的地数をT、セル数をVとすると、構築は概ねO(TV log V)、場の保存はO(TV)です。

渋谷では各出入口の歩道側の到達点を目的地として場を共有します。全目的地へ到達できない孤立した庭などのセルは有効グリッドから除外します。目的地同士が分断されている場合は初期化をエラーにし、接続不良のまま群集を生成しません。

近距離の見通しと、方向場の先読み

渋谷の通常の経路誘導では、個別目標まで10m以内で、人物半径に0.015mを足した余裕を含めて直進できる場合、その目標へ直接向かいます。それ以外は周囲3×3セルの見通せる候補から D + 0.1 × 現在位置からの距離 が最小のセルを選び、方向場を最大3セル分先読みします。横断歩道で人を避けて白線の外側に出た場合、通常の候補が見つからなければ周囲5×5を探し、さらに必要なら見通せる最寄りの経路セルを探して戻ります。

ポリゴンの包含判定には穴も含む境界との交差回数を用い、半径の余裕には境界辺までの距離を調べます。1m幅の行と4m四方の区画で辺を索引化し、点・線分・近接境界の照合候補を絞ります。方向場をセル間で双線形補間する処理はありません。

AABBを使う他シナリオでは、目標への見通しがあれば直接誘導し、遮られれば方向場を参照します。固定0.58mの余裕を付けたAABBと線分の交差は、各軸の区間の重なりを調べるスラブ法で判定します。通行不可セルでは周囲5×5から回復先を探します。PBRTはスラブ法の技術解説として挙げています。[12]

距離場は目的地を共有する人の道しるべです。方向を取り出す際に比較する値は隣接セルの D(v) だけです。さらに各人は直進できる区間を選び、局所回避で周囲をよけるため、歩いた距離はグラフ上の最短距離と異なる場合があります。

文献との対応　Emersonの解説と共通するのは目的地別の方向場を共有する部分です。同書のタイル階層・タイル間のポータル探索は未実装です。Continuum Crowdsは比較対象です。群集密度で変化する場とEikonal方程式は、この実装では使いません。[2] [8]

渋谷の歩道では、混雑した進路の少し先を見てよける

SidewalkPassing は通常歩行の誘導方向を調整する渋谷専用の処理です。15ステップごとに人物IDで時刻をずらし、同じセルに複数の人がいて目的地まで3m以上ある場合に、5m以内で見通せる歩行者を調べます。前がふさがれていると、相手の0.4秒先の位置を使って直進と左右25°・50°・77°の計7方向を比較します。選んだ方向に歩道内を3.5m進める地点（届かなければ1.6m）を一時的な目印にします。横断歩道への誘導中や退避中、戸口で譲っているときには、この目印を解除します。

実装箇所　Navigation.buildField / direction / urbanDirection / lineOfSight、UrbanGeometry / PolygonRegion、SidewalkPassing.guide。

04 / SPATIAL QUERY近くの人だけを高速に探す

全員が全員を調べると候補数はO(N²)になります。Fluxityの SpatialGrid は、経路探索の格子とは別に、CPU上で一辺2.4mの均一な格子（Uniform Grid）に人物を登録します。

  1. 各人物が属するセルを求め、セルごとの人数を数えます。
  2. 人数の累積和（prefix sum）から、各セルが使う配列区間を求めます。
  3. 人物IDをセルごとの連続領域へ配置します。比較ソートは使わず、Counting Sort型に並べます。

再構築はO(N+C)です（Cはこの近傍グリッドのセル数）。各人物は自分のセルと周囲8セルを走査し、距離が2.4m以下の相手を局所回避に使用します。配列は再利用され、通常の再構築で人物ごとの配列・オブジェクトを生成しません。

局所回避の上限96は、距離を測る前の候補数です。自分以外の人を走査順に数えるため、距離外の人も96件に含まれます。セル内の開始位置を人物IDでずらしていますが、セルを訪れる順序は固定です。そのため密集時には近くの相手を見落とすことがあります。

Steering.compute が行う近傍走査の上限は全員でO(96N)です。ここでの2.4mは§5の局所回避に用いる半径です。§3の歩道の進路選択など、同じグリッドを使う別の処理は用途に応じた範囲を調べます。Le GrandのGPUによる衝突候補の絞り込みは、空間分割の考え方を説明する参考文献です。[9]

実装：SpatialGrid.rebuild、Steering.compute。

05 / LOCAL STEERING反発・減速・予測を混ぜる局所回避

通常歩行を担当する Steering.compute は、目標へ向かう速度に、身体の間隔を保つ反発、前の人に追いついたときの減速、接近予測に基づく回避を加えます。以下の式と数値はFluxityが実際に使う規則です。ReynoldsのSteering Behaviorsは局所行動の背景資料、Boidsは比較対象です。Fluxityの歩行者は周囲の平均速度にそろえたり、群れの中心に集まったりする規則を使いません。[3] [4]

pᵢ, vᵢ, rᵢ
人物iの位置・現在速度・半径。
dᵢ, sᵢ
誘導方向と、このステップでの希望速度。sᵢには分岐での減速や横断時の退避倍率を含む。通常のdᵢは単位ベクトル。
q, R
相対位置 q = pⱼ − pᵢ、半径の和 R = rᵢ + rⱼ。
right(dᵢ)
右向きの成分 (dᵢ.z, −dᵢ.x)。
k
回避の強さ（avoidanceStrength）。初期値は1。画面の「Personal space」で0〜2.5の範囲を指定でき、計算側は0〜3を受け付ける。

青点滅・赤で縁石に近づくと、進入方向の成分を弱めます。その後の内積にもこのdᵢを使うため、縁石付近の「前方距離」にはこの減速が反映されます。

5.1 パーソナルスペースの反発

相手までの距離が R + 0.34m 未満なら、相手から離れる成分を足します。これは速度への補正であり、人物同士のめり込みを幾何学的に必ず解消する位置補正ではありません。

δ = |q|
c = 通常は3.6、相手が出入口を通行中なら8
Sᵢⱼ = −(q / δ) × min(2.4, c × (R + 0.34 − δ))
Sᵢ = 条件 δ < R + 0.34 を満たす近傍の Sᵢⱼ の総和

位置がほぼ一致する場合は、IDの大小で符号が反対になる微小ベクトルを使い、ゼロ除算と完全な対称状態を避けます。

5.2 前の人に追いつくと減速する

前方成分 f = q・dᵢ が0〜1.8m、横方向成分の絶対値が R + 0.2m 未満で、相手との前方速度差が0.15m/sを超える場合に減速します。

c = q.x × dᵢ.z − q.z × dᵢ.x
closing = sᵢ − vⱼ・dᵢ
b_follow = (1 − f / 1.8) × min(0.85, closing × 0.5)
brake = 対象となる近傍の b_follow の最大値

5.3 最近接時刻を予測し、直進・左右・減速を選ぶ

自分が希望速度 sᵢdᵢ、相手が現在速度 vⱼ を維持すると仮定します。相対位置の二乗距離 |q − wt|² をtで微分して0と置くと、最近接時刻t*が得られます。

w = sᵢdᵢ − vⱼ
t* = (q・w) / |w|²
δ* = |q − wt*|
u = (1 − t* / Hᵢ) × (1 − δ* / (R + 0.35))

f > 0、|w|² > 0.08、0 < t* < Hᵢ、δ* < R + 0.35m のとき、衝突のおそれがあると判定します。四候補を選べる通常歩行では個人別に1.4〜1.85秒先を予測し、選択の対象外ではHᵢを1.6秒とします。緊急度uが最も高い相手を記録し、1.25u が0.075を超え、判断を見直す時点に達すると、四候補を評価します。

試す速度は、前方・右方向の順に希望速度に対する倍率で表すと、直進（1, 0）、右へ（0.88, 0.64）、左へ（0.88, −0.64）、譲る（0.35, 0）です。進路前方の空きを評価するため、q・dᵢ < −0.3 の後方の相手をこの比較から外します。その他の近傍は現在速度を維持すると仮定し、各候補の先読み時間内で最も危険な接近を評価します。そこに基礎コストを加えます。直進は0、右は0.08、左は0.25、譲る場合は人によって0.11〜0.28です。すでに片側を選んでいる場合、異なる側・直進・減速への変更には0.36を加えます。後方から来る人にも近距離の反発は働きます。

評価がよい候補から、0.65秒先まで壁・路面・赤信号の制約に収まるかを調べます。すべて通れない場合も減速を選び、最終位置は§6の境界処理で確定します。危険が続く間は約0.42〜0.62秒おきに判断を見直し、最後に判断を必要とする危険を検出してから0.38秒、選択を記憶します。横へよける方向が新しく決まり、衝突予測まで0.65秒を超える余裕があれば、横方向の補正を0.12秒かけて立ち上げます。急接近時はすぐに回避します。

歩行に適用する補正の強さは、その時点の危険に合わせます。左右を選んだときは、候補の相手がいる間、横方向の補正に希望速度の0.30倍を下限として設けます。譲るときは min(0.62, 0.22 + 0.46 × 最大緊急度) を減速係数の下限にします。予測上の相手がいなくなれば両方の補正を解除し、次の瞬間に同じ相手が再び現れたときのために選択だけを短く保ちます。戸口付近では戸口の通行制御が優先されます。四候補を比較するのは、戸口用に指定されたセルの外で、希望速度と回避の強さがともに正のときです。

比較対象（未実装）　Velocity Obstaclesは相手の運動から衝突に至る速度の集合を求め、ORCAは互いの回避負担を分けて半平面制約から速度を求めます。Fluxityの四候補の比較で得られるのは、横へよける側と減速するかどうかです。実際に歩く速度は次の合成式で計算します。[5] [6]

5.4 合成・滞留脱出・壁回避

v_desired = sᵢdᵢ × (1 − brake × min(1,k))
          + k × (Sᵢ + lateral × right(dᵢ))
          + 戸口や退避先の縁石で進路を譲る成分 + 滞留時の右寄せ + 壁・外周からの反発
最後に |v_desired| を 1.12sᵢ 以下へ制限

実際の速さが個人の基準希望速度（preferredSpeed）の20%未満の状態が2秒を超えて続くと、sᵢが正の場合に 0.3 × right(dᵢ) を追加します。これは対向流が同じ位置で止まり続けるのを緩めるための規則です。

渋谷では歩行可能ポリゴンの境界が rᵢ + 0.75m より近いと、通常は内側へ押し戻します。横断中に人をよけるときは白線外の許容領域まで使い、その外縁からの反発を使います。他シナリオでは建物AABBの最近点から離れる成分を加えます。シーン外周にも反発があります。壁からの反発、信号による制限、滞留時の右寄せは回避の強さを0にしても働きます。

5.5 肩が触れた後の反応

円として表した体が接し、実際の相対速度のうち相手に近づく成分が0.22m/sを超えたとき、接触側と逆に上体を短く傾けます。傾きは接近速度に応じて最大0.21radとなり、通常歩行では一時的な減速にも使います。体の間隔が半径の和＋0.055m以内の間は同じ接触として扱い、この距離を離れて約0.24秒経過すると次の反応が可能になります。混み合って肩を並べて立っている間に、反応だけが繰り返されることを防ぎます。

実装箇所　EncounterState、Steering.compute / chooseManeuver。

06 / MOTION速度を更新してから位置を進める

通常歩行では、§5で合成した速度に、必要に応じて店舗前の待機や人の間隔を保つための制限を加えます。こうして得た目標速度へ0.3秒の応答時間で近づくように加速度を求めます。

a = (v_desired − v) / 0.3
a ← 長さを最大 3.8 m/s² に制限
v′ = v + aΔt
|v′| の上限 = max(個人の基準希望速度 × 横断退避倍率 × 1.12, |v| − 3.8Δt)
p′ = p + v′Δt
Δt = 1/30 s（通常のWorker実行）

実装は半陰的オイラー法（semi-implicit Euler）の順序で、更新後の速度から次の位置を求めます。横断退避倍率は通常1です。速度設定を下げた直後は、現在速度から1ステップで3.8Δtだけ減らした値を上限計算に含め、段階的に減速します。

壁との接触は位置を補正する

位置更新後、人物の半径と余裕0.015mを含めてシーン外周の内側に収めます。渋谷では開始点から予定点までの線分を検査し、歩道や横断歩道の境界にかかると接触手前で止め、境界に沿って移動できる成分を残します。建物をAABBで表すシナリオでは、拡張AABBに入った予定点を最も近い面まで押し戻します。

戸口付近では身体の間隔を確認し、渋谷で予定の一歩が車体にかかる場合は元の位置にとどまります。最後に v = (確定した位置 − 旧位置) / Δt として実速度を求めます。この位置補正による減速は、積分時の上限3.8m/s²を超える場合があります。

身体の向きと歩行アニメーション

速度が0.045m/sを超えると、移動方向 atan2(vx, vz) へ、最短の角度差を使って最大3.5rad/sで身体の向きを近づけます。これは見た目の向きの制限で、速度ベクトル自体の旋回速度を制限する処理ではありません。

歩行位相は phase += speed × Δt × 4.5 とし、移動距離に連動させます。位相を毎回2πへ折り返さないことで補間の継ぎ目を避けます。速度0.06m/s未満はIdle、2.2m/s超はRun、それ以外はWalkとして描画へ渡します。

首の向きと、分岐で一瞬迷う動作

信号待ちでは、歩行者用の青点滅・赤による縁石での減速に入った人にだけ、次に見回すまでの時間を割り当てます。待ち時間は0.65秒に指数分布の時間を加え、周囲への関心が高い人ほど平均の間隔を短くします。見る先は、進みたい横断歩道の向こう側、その側にあるこちら向きの信号、近くを歩く人です。すれ違いでは、横へよける判断をした人の一部が、通る隙間に先に顔を向けます。首は身体に対して左右最大1.18rad、最大2.8rad/sで動き、一度選んだ方向を0.45〜1.05秒見てから正面へ戻します。人物視点のカメラも首の向きを反映します。

分岐の判定は、一人ずつ時刻をずらして行います。交差点の入口や障害物の手前で、目的地に向かう11方向を10m先まで調べます。通れない地面で分かれた二つの進路がどちらも目的地に近づき、残りの経路長の差が3.5m以内なら、迷う余地があります。その場所に来たときに一度、道に慣れている度合いに応じた確率で反対の候補にも顔を向け、0.55〜1.25秒の間、希望速度を35〜62%にします。その後は元の目的地へ進みます。渋谷の横断中や信号待ち、戸口での通行制御中には、この減速を加えません。

実装：PedestrianAttention、Navigation.alternativeAtFork、Simulation.step / writeSnapshot。

07 / SHIBUYA SCRAMBLE歩行者・東西の車・南北の車を順に通す

渋谷ステージはPLATEAU渋谷区2025年度の建物・道路データを使います。建物はLOD2を優先し、背景は約500m四方、歩行計算は中心250m四方に限定します。元データの歩道に、地理院空中写真を参照して調整した駅前広場・植栽除外と5本の横断歩道を重ねています。横断歩道の幅は6.5〜11mのデモ設定で、測量済みの路面標示や現在の信号設備を表すものではありません。

歩道と横断歩道のポリゴンは取り込み時に和集合・差集合を計算し、描画と経路探索の共通データにします。横断歩道の白線は車道面で切り抜きます。描画バイナリのSHA-256を地図に記録して読み込み時に検証するため、地図と一致しない描画バイナリは読み込みエラーになります。地面は平坦化し、建物は元の形状を保って建物ごとの最低標高を差し引きます。坂道・駅構内・デッキ・地下通路の多層移動は対象外です。

CrosswalkFlowは目的地への方向場をたどり、次に使う横断歩道を特定します。両側の歩道まで身体の幅を確保できる横断経路を、白線の幅方向に複数用意します。歩道上で入口まで12 m以内に近づいた人は、その中から1本を選びます。一方向の流れでは幅全体を使い、逆方向の利用者が多いほど新たに入る人の候補を進行方向の右側に寄せます。すでに選んだ人は自分の経路を保ちます。

歩行者の青

5本の横断歩道が同時に開き、斜め方向も渡れます。車両用は全方向で赤です。人を避けるときは白線の外側0.8mまで使えます。

歩行者の青点滅

新たに横断する人は縁石で待ちます。横断中の人は、今の位置から到達できる近い歩道へ渡り切るか引き返します。退避時は元の希望速度を最大25%引き上げます。引き上げは2.8 m/sまでで、もともとそれ以上の人は自分の希望速度を保ちます。

歩行者の赤

新たな横断は縁石で待ちます。退避中の人は点滅時に選んだ歩道を目指し、着地点の前にいる人は道を譲ります。横断中の人が残っている間、車両用信号は全方向で赤を保ちます。

歩行者用の二灯は上に赤の停止人形、下に青の歩行人形を表示します。車両用の三灯は運転者から見て左から青・黄・赤の順です。道路交通法施行令第2・3条 · 警察庁「歩車分離式信号に関する指針」

縁石への接近と退避

横断中に青点滅・赤を迎えると、CrossingExitsが身体全体の収まる着地点を選びます。縁石の内側へ直進できればその距離を使い、直接見通せない候補には横断領域の4近傍グリッドを幅優先探索して経由点と道のりを求めます。元の目的地や列の混み具合は、この最初の歩道選びに使いません。

青点滅・赤で歩道にいる人について、進行方向にある歩道境界を調べます。信号待ちの注視対象は、縁石で方向を弱める前の進路から選びます。境界の先が歩行可能な横断領域へ開いている場合だけ停止対象とし、建物壁は停止線として数えません。停止位置までの進行方向距離が3m未満なら、歩道境界の法線方向の成分を弱めます。法線方向の減速幅は2.2m、停止位置には有効半径に加えて0.08mの余裕を設けます。減速を局所回避より前に適用し、境界に平行な移動は残します。

局所回避の押し出しで車道へ入らないよう、最後にも歩道ポリゴン内へ移動を制約します。歩道内の判定・経路誘導・減速・移動制約・横断人数は、いずれも人物半径＋0.015mで統一します。横断中の人は、全身が歩道に収まった時点で元の旅程に復帰します。

CrossingClearanceは退避中の進み具合を2秒ごとに確認します。進めないときも同じ歩道を目指し、混み合った場所では元の着地点から12 m以内で、途中の列と着地点にいる人数を考慮して候補を選び直します。縁石の近くでは歩道へ直接上がる短い経路も試します。退避中の人がいて縁石が混雑すると、歩道側では縁石手前2.1 mの範囲で後退を促し、着地点を塞いでいる人も斜めに退きます。

線分を検査してから、境界に沿って滑らせる

PolygonRegion.lineInsideは始点・終点の包含に加え、移動線分と境界の交差、線分と各境界辺の最短距離を調べます。終点だけが有効でも、その途中で建物の穴や領域外を横切る移動は採用しません。境界は空間索引で絞り込みます。

予定移動が通れない場合は、最大12回の二分探索で接触手前を求め、残った移動から外向き法線成分を除去します。この処理を最大2回行い、横断歩道の端に沿う移動を残します。Float32への格納で境界外に丸められたときは、最大4回の微小な内側補正を試します。補正量は予定移動距離を超えないようにし、安全な表現可能位置が得られなければ元の位置を維持します。

回帰テスト用の実装。 synthetic-shibuya.tsでは旧来の十字型交差点を再現し、ScrambleGeometryが区間の和集合と凸領域への投影で歩行範囲を求めます。アプリの渋谷ステージが使うのは、上記のUrbanGeometryとPLATEAUのポリゴンです。

自動周期はシミュレーション時計で進む

TrafficSignalは歩行者・東西の車・南北の車のうち、一度に一方向を通す状態機械です。自動モードは2020年8月25日18時ごろの現地観測を基に、下表の秒数と順序を使います。基準周期は140秒で、横断中の人や交差点を抜け切っていない車がいると全赤を延長します。手動モードは次に通す方向か全赤を指定し、同じ青点滅・黄・全赤の移行を経ます。各段階の時間はシミュレーションの再生中に進みます。設定秒数の出典（現地観測） · 関連研究（背景資料）

車の加減速と歩行者との間隔

車は東西・南北各2本、計4本の左側通行の経路を走ります。車線を折れ線で表し、それに沿った距離で位置、車間、停止位置を管理します。前が空けば車ごとの巡航速度（20〜30 km/h）へ加速し、前走車には停止時の車間2 mと車ごとの追従時間（1.35〜1.85秒）を使って減速します。黄に変わった瞬間、停止線までの距離が制動距離 v² / (2 × 2.3) より短い走行車だけに進入を許します（v は m/s、通常の減速度は2.3 m/s²）。進入前の車は赤で停止線の手前に止まります。

各ステップで、歩行者の予定移動が現在の車体と重なればその一歩を止めます。次に、採用した歩行者の移動線分を車線に投影します。このとき車体の長さ・幅、曲線部で車体の角が動く分、手足の動きを含む歩行者の余裕（0.78 m × 体格倍率）を含め、重なる区間の手前で車の移動を制限します。この判定は歩行者同士の回避強度がゼロでも働きます。

08 / TIME & DATA計算の時計と、画面の時計を分ける

固定刻みと、追いつき処理の上限

Fluxityでは1本のWeb Workerが歩行者・車両・信号を1/30秒の固定刻みで更新し、メインスレッドが画面を描きます。時間を蓄積して固定幅で消費する仕組みは、Fiedler（2004）が解説した方式と共通です。[10]

Workerは8 ms間隔のタイマーが呼ばれるたびに、前回からの実時間差を最大0.1秒に制限し、速度倍率を掛けて蓄積します。蓄積は最大3ステップ分で、1回の呼び出しで最大3ステップを実行してから最新状態を送ります。長い遅延の際は超過時間を捨てます。

SoAと二重状態

位置・速度などを項目別のTypedArray（x[]、z[]、vx[]など）に格納するStructure of Arrays（SoA）形式です。局所回避はステップ開始時の位置・速度をcurrentから読み、決まった移動先をnextに書きます。戸口付近では、先に処理した人が空けた間隔も使います。続いて車両が各人の開始位置と移動先を使って進める距離を調べ、人物の入れ替えを処理してから両配列を交換します。

Snapshot転送と表示補間

Workerは1人分の位置・向き・首の角度などを15個のFloat32（60バイト）にまとめ、その後ろに車両スロットごとに5個のFloat32（20バイト）を並べます。信号も同じメッセージで届きます。描画時には画面に映る人物を1人64バイト（4個のvec4）に詰め、GPUへ送ります。

Workerとメインスレッドは4個のArrayBufferを循環させます。メインスレッドは直前と最新の2状態を補間用に保持し、古いバッファを返します。空きがない場合、Workerは途中の送信を省き、バッファの返却時に最新状態を送ります。初期化の世代番号で古いメッセージを除外します。

p_render = (1 − α) p_previous + α p_current
α = clamp((受信後の実時間 × 速度倍率) / Snapshot間のシミュレーション時刻差, 0, 1)

上式の実時間は最新Snapshotの受信からの経過秒数です。2状態のシミュレーション時刻が同じなら分母に1/30秒を使います。身体の向きは最短の角度差、歩行位相は連続値で補間し、最新位置に達するとそこで止めます。人物が入れ替わったスロットには新しい位置を使います。

車が走る渋谷では、前後のSnapshotがちょうど1ステップ差で、歩行者・東西・南北の灯色と全員・全車両の世代が一致する場合に補間します。それ以外は歩行者と車をともに最新位置で表示します。

実装：SimulationWorker、AgentData、SnapshotTimeline、InstanceBuffer.update。

09 / REPRODUCIBILITY初期化・目的地更新・再現性

Random.nextはMulberry32の定数 0x6d2b79f5 と乗算・XORによるビット混合を実装し、体格・速度差・外観・初期配置などに使う乱数を生成します。原実装は32ビット整数で状態を更新します。Fluxityは初期シードを符号なし32ビット整数に変換した後、状態の加算結果をJavaScriptのNumberで保持するため、長期間の出力列が原典と一致する保証はありません。[11]

同じ動きを再現するには、コード、シード、設定に加え、ステップ列と設定を変更するタイミングをそろえます。異なるブラウザ間でのビット単位の一致は未検証です。

周囲を見る頻度・道への慣れ・衝突の先読み時間・譲る傾向は、シード、人物スロットID、人物の世代から決めます。注視の間隔や持続時間には各人物専用の乱数列を使います。出入口でそのスロットが別人に入れ替わると、性向と行動タイマーも新しくなり、直前の人物の姿勢は引き継ぎません。

初期配置は試行回数を制限した拒否サンプリング

スポーン領域から候補点を取り、通行可能性と既配置人物との距離を調べます。最大100回まで試し、戸口周辺では肩幅を確保し、それ以外では試行が進むにつれて間隔条件を緩めます。渋谷では全目的地へ到達できる歩道に限ります。試行が尽きたら、事前に検査したセルのうち同じスポーン領域内を優先して選び直します。この代替配置では他の人と重なる場合があります。

渋谷の既定の旅程と出入口

アプリの渋谷ステージは50か所の戸口と、東西南北に分布する10か所の街路端を目的地に使います。PortalTripDemandはシード・人物ID・世代ごとに旅程の目的を抽選します。設定確率は通り抜け（街路→別方面の街路）50%、来店（街路→店）25%、外出（店→街路）25%です。これは旅程を生成するための確率で、完了人数の比率は混雑や出入口の空きに応じて変わります。

行き先の抽選では入口の幅を重みに使い、同じ幅なら店は近いほど、街路端は遠いほど選ばれやすくします。初回だけはスポーン領域の各人に目的地を割り当てます。以降は1人の退出が完了したステップで、別の出入口から次の1人が現れます。PortalFlowは新しい旅程の出発地として希望する種類の出入口を優先し、空きがなければ他の種類も使います。補充できる場所が空くまで退出を待つため、総人数は一定です。

ほかの4シナリオでも退出と補充にはPortalFlowを使います。広場では出発した出入口を除き、距離と乱数で次の目的地を選びます。双方向通路・ボトルネック・交差流では、出発した街路端に対応する行き先をシナリオが指定します。

戸口への合流と歩道の譲り合い

歩行者は共有経路から戸口や街路端の短い通路へ入り、終端に近づくと徐々に姿が消えます。渋谷の幅のある戸口では中央のレーンから人が店を出て、その脇のレーンから人が入ります。入店する人は現在位置から横移動が少なくて済むレーンを先に試し、塞がっていれば同じ戸口の別のレーンを試します。

渋谷の既定の回避設定では、出入口に近づいた人は自分の前方2.2 m以内に見える相手の位置と速度から、互いの進路が重なるかを判断します。ほぼ停止した相手には体の向きを使います。歩道上の人は出入口を通っている人に道を譲り、空きへよけるか短く待ちます。入店列に並ぶ人は、戸口から2〜17 mの歩道で、ほぼ止まっている前の人までの進行方向の間隔が身体半径の和＋0.70 mを下回ると、0.35秒間、目標速度をゼロにします。

店から出る人と、戸口に斜めに入る人の進路が1 m以内で重なると、入る人が譲ります。もう少し離れていれば、どちらかが0.6秒以上足止めされたときに譲ります。通常の歩道でも前方に遅い人や対向者が見えたら、15ステップ（0.5秒）ごとに進路を見直し、歩道内の最長3.5 m先の空きを目指します。戸口付近で一歩の移動を決めるときは、出入り中の人には肩幅の余裕を、歩道上の人どうしには身体半径の和を確保します。

比較実験で切り替える出入口の滞留対策

PortalDeadlockRecovery（メタAI）は実装済みで、現在の渋谷の既定設定では無効です。 上記の戸口の合流・譲り合いは通常の歩行処理として動きます。滞留対策を明示的に有効にした場合は、目的地から12 m以内にいる人の進みと通過人数を1秒ごとに調べ、滞留が続いたときだけ通過・待機・脇へ退く指示を出します。

compare-portal-recovery.tsは旧配置（5店舗・北側の街路端1か所）で、滞留対策なし・北西店のみ・全地点の3条件を比較します。compare-shibuya-destinations.tsは滞留対策を無効に保ち、店舗数と街路端の配置を組み合わせた4条件を比べます。後者のうち50店舗・全方向の街路端が現在のアプリの配置です。

旅程と配置は Random、Simulation、PortalTripDemand、shibuyaシナリオ、出入口の配置データ を参照してください。出入りと歩道での行動は PortalFlow / DoorwayClearance、DoorwayCourtesy、DoorwayHeadway、SidewalkPassing、滞留対策を切り替える比較実験は PortalDeadlockRecovery に対応します。

表示される統計の定義

  • Mean walking speed は、そのステップに各歩行者が実際に進めた距離をΔtで割り、戸口を通行中の人も含めて全員で平均した速度です。
  • Slow / stopped は、実際の速度が各人の希望速度の45%を下回った人数の割合です。希望速度0の人は分子に入りません。
  • Waiting は、青点滅・赤で歩道上にいて、そのステップで縁石への接近判定に入った人数です。減速しながら進んでいる人も数えます。
  • Crossing は、そのステップの移動後に横断用の領域で車道を占めている人数です。渋谷では、中心が横断領域にあり、身体の円（半径＋0.015 m）が歩道に収まらず、中心が車道内にあるか車道の縁にこの半径まで近づいている人を数えます。横断歩道のそばでも、車道から離れた店舗の戸口を通る人は含みません。

WaitingとCrossingは各ステップの人数です。一時停止中の手動操作でも要求した方向と現在の灯色を表示します。歩行者用が青になるとWaitingは直ちに0になり、歩行再開後は移動に合わせて人数を更新します。

11 / VALIDATION & LIMITS自動テストの対象とモデルの限界

既定の渋谷地図では、通行可能な格子セルから全目的地へ到達できること、1,000人が全赤で歩道にとどまり青で横断を始めること、20,000人の初期配置と短時間の更新で通行範囲を守ることを検査します。車両については、黄に変わった瞬間の停止判断、歩行者が車道に残る間の両方向の停止、曲がった車線での車体と歩行者の間隔も検査します。

共通のテストには、シードによる再現性、対向者の回避、加減速、Snapshotの返却と表示補間があります。旧配置の5店舗すべてへの入店や、滞留を検知して通行順を決める補助制御は、それぞれ専用の設定で検証します。テストの実装一覧

境界実装上の意味
人物同士の重なり通常の歩道では速度補正で回避する。接触時に姿勢を変えて減速するが、過密時や候補の見落としで体が重なり得る。戸口には専用の通行制御がある。
渋滞・デッドロック通常の渋谷では、すれ違う側を保持し、店から出る人に場所を空ける。それでも歩道の幅や人の集中によって列が動けなくなることがある。出入口単位で通行順を指示する補助制御は既定で無効。
最短経路・動的混雑静的な共有場。混雑で大域経路を再最適化せず、個別軌跡の最短性も保証しない。
境界と時間刻み渋谷の歩行境界は静的な平面ポリゴンで、移動線分に人物の半径を加えて検査する。手続き生成シナリオでは外周と長方形の障害物に位置補正をかける。Simulation.stepは0秒超、0.1秒以下を受け付け、Workerは毎回1/30秒を渡す。
地図と高さPLATEAUの版年は形状の取得年ではない。地面は平坦化し、横断歩道・信号位置・駅前補正はデモ用の調整。地表の建物輪郭で移動を制約し、屋根形状を歩行衝突に直接使わない。
実測との対応信号の基準時間には渋谷駅前の観測記録を使用する。歩行速度の個人差・視線や迷いの頻度・回避時のコストはデモ用の調整値。実在の渋谷の流量や避難時間を予測するための校正は行っていない。
計算量と性能人数をN、人物用グリッドのセル数をCとすると、索引の再構築はO(N + C)。局所回避で最初に調べる他人は1ステップに最大96N人分。渋谷の歩道境界の検査、出入口での間隔確認、車線ごとの歩行者の移動線分の検査は別にかかる。
